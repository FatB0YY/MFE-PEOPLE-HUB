# MFE People Hub

A completed take-home assignment on micro-frontends: a host shell and two independent micro-frontends built on Module Federation 2.0.

## The assignment

Build a small application made of a host shell and two micro-frontends.

- The first one displays and edits a user profile.
- The second one shows a card for the same user.
- After saving, the card must update without a page reload.
- The micro-frontends must not depend on each other directly.
- Loading and error states are required.

Also assessed: a typed contract between the micro-frontends, subscription cleanup, and the application's behaviour when one of the modules fails to load.

## Stack

React 19, TypeScript 6 (strict), webpack 5 with `@module-federation/enhanced`, react-router 8, Tailwind CSS 4 with shadcn/ui-style components, Mock Service Worker instead of a backend, pnpm workspaces, ESLint 10 with type-aware rules.

Node 22.22+ required (react-router 8 baseline). Verified on Node 24.21 and pnpm 12.6.

## Running

```bash
pnpm install
pnpm dev            # all three dev servers; open http://localhost:3000
```

| App           | Port | Notes                             |
| ------------- | ---- | --------------------------------- |
| `host`        | 3000 | the shell, entry point for review |
| `mfe-profile` | 3001 | also serves a standalone page     |
| `mfe-summary` | 3002 | also serves a standalone page     |

```bash
pnpm dev:host / dev:profile / dev:summary   # one app at a time
pnpm build          # production build of all three
pnpm typecheck      # tsc --noEmit across packages
pnpm lint           # ESLint
```

Two notes. Remote types are generated by Module Federation into `apps/host/@mf-types`, so `pnpm typecheck` in the host only passes after the remotes have been started or built at least once. And `pnpm build` deliberately excludes the mock backend, so use `pnpm dev` to look at the application.

## Layout

```
apps/host/           routes, layout, header, RemoteBoundary
apps/mfe-profile/    profile form, tabs as sub-routes; exposes ./ProfileApp
apps/mfe-summary/    read-only card; exposes ./SummaryCard
packages/contracts/  User, AppEvents, event bus, UserApi, completeness rule
packages/api-client/ UserApi over fetch, stateless
packages/mock-api/   Mock Service Worker handlers, development only
packages/ui/         components and theme tokens
```

The micro-frontends share nothing but `@people-hub/contracts`. Data travels over HTTP.

## Key decisions

**A typed event bus on eventemitter3.** The modules talk through a single bus: the publisher does not know its subscribers, so `mfe-profile` can announce a save without importing `mfe-summary`. Nothing wraps the library — `appBus` is an `EventEmitter` parameterised by the contract's event map, so an unknown event name or a wrong payload is a compile error. `on` returns no unsubscribe function, so every subscription keeps a named handler and pairs `on` with `off` in the effect cleanup.

**`contracts` is a singleton, the data layer is not.** The bus keeps subscribers in module memory, so a second copy would silently stop events from crossing module boundaries. The API client, by contrast, holds no state — every bundle carries its own copy, and the single source of truth lives behind the network. There is no shared mutable state between the micro-frontends.

**Nested routing with a shared router.** The host owns the prefix and hands it over whole (`/profile/*`); the module describes its subtree with relative paths and never learns where it is mounted. A 404 inside the prefix is the module's problem. `react-router` is a singleton — two histories on one page would hide the module's navigation from the host.

**Each consumer loads its own data and guards against stale responses.** Every consumer calls `getUser()` on mount and then subscribes, so a late subscriber never sees an empty screen. That cure creates a race: a response to a request sent before the save can overwrite fresher data. Each consumer numbers its requests and drops outdated ones.

**`shareStrategy: 'loaded-first'`, not the default.** With the default `version-first` the runtime initialises sharing across every declared remote before resolving any shared dependency, so a single unreachable remote blanks the whole page before the first render — `RemoteBoundary` never gets a chance. The default solves version skew between independently built bundles; this repository has none by construction.

**Remotes load through the runtime API.** `RemoteBoundary` is an ErrorBoundary plus Suspense with a retry button. An honest retry needs both `registerRemotes(..., { force: true })` and a fresh `lazy()`, because the federation runtime caches the failure and `React.lazy` caches the rejected promise. A compiled `import('summary/SummaryCard')` keeps pointing at the container captured earlier, so `loadRemote` is used instead; the type link is preserved through `typeof import(...)`.

**Tailwind across bundles.** Preflight ships once, from the host; remotes add it only in their standalone entry. Theme tokens live in one file and are imported by all three apps, otherwise identical utility classes would carry different values and the last bundle loaded would win. Each app scans both its own sources and the shared package.

**A monorepo does not contradict independent deployment** — Module Federation provides it, not the number of repositories. Shared packages ship TypeScript sources and have no build step; Nx and Turborepo are not worth their configuration at three apps.

## What to look at

Open **Профиль**, change the name and fill in the position, press **Сохранить**: the card updates without a reload, the completeness indicator goes from 67% to 100%, and the header initials change too — three independent subscribers to one event.

Switch between the tabs: the address changes to `/profile/contacts` and back, both open directly. The second tab has no fields — the model carries only what the card can show; the tab is there to demonstrate nested routing.

Toggle **Сымитировать ошибку API** in the header and navigate between pages: both modules show their own error state and a working retry.

Start the apps separately and stop the one on port 3002: the page keeps working, the card is replaced by a retry panel, saving still works. Bring the module back and press retry — the card returns without a reload.

## Limitations

No tests and no CI — deliberately out of scope. Remote addresses are hardcoded rather than read from environment configuration; making them dynamic is the obvious next step. The mock keeps state in page memory, so a reload resets it.
